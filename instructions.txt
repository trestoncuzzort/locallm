--------------------------------------------------------------------------------
1. WHAT THIS IS
--------------------------------------------------------------------------------
A local, autonomous self-rewarding loop that trains a small model to fix its own
mistakes. The model proposes solutions; an OBJECTIVE verifier (unit tests) decides
ground truth; preference pairs are learned from that verdict. The signal is anchored
to executable tests specifically so the loop self-IMPROVES instead of self-deceiving
(no ungrounded LLM-as-sole-judge reward hacking).

Thesis: "train on current failures." Tasks nothing solves become the curriculum
for the next round and the seed for future training.

2. CURRENT STATE (verified working, 2026-07-25)
--------------------------------------------------------------------------------
Runtime:
  - Ollama v0.32.3 (per-user), model llama3:8b-instruct-q4_K_M pulled (4.9 GB).
  - Generation runs on system Python 3.14 with only `requests`. Endpoint live.

Pipeline (forge.py), fully debugged and validated:
  - ACTOR: samples K candidates per task from Ollama (1 greedy anchor + diverse rest).
  - VERIFY: runs each candidate against unit tests in an isolated subprocess
    (python -I, timeout, coarse banned-op filter). This is the ground-truth reward.
  - PAIR: chosen = best verified candidate. A pair is emitted only on a REAL
    correctness gap (chosen passes / rejected fails), else a conciseness margin
    of >= 40 chars. Never on timing noise.
  - CRITIC: writes an honest rationale for why chosen beat rejected, framed by the
    true reason (correctness vs conciseness). Explains the verdict; never overrides it.
  - CURRICULUM: all-fail tasks -> failures.jsonl.

Last run (6 tasks): 5 solved, 3 valid DPO pairs (2 correctness + 1 conciseness,
all re-verified: chosen passes, correctness-rejects genuinely fail), spiral -> curriculum.
Output: data/dpo_pairs.jsonl (Unsloth DPO schema), data/failures.jsonl.

Training half (train_dpo.py): written, NOT yet run. QLoRA DPO -> GGUF -> back into
Ollama, closing the loop.

1. DPO IS THE WRONG PRIMITIVE FOR ALL-FAIL INJECTION. (Contrarian + First Principles,

   token log-ratio between chosen and rejected. An injected canonical solution shares
   almost no tokens with the model's mangled attempt, so the gradient is dominated by
   nuisance STYLE (names, idioms, structure) — you teach "look like the teacher," not
   "fix the bug," and that style pressure can REGRESS your 0.88 baseline on tasks it
   already passes. Correct primitives:
     - Genuinely-absent capability (0/K even at high budget): SFT on the verified
       reference. Not DPO.
     - Near-frontier (partial pass, e.g. rle=4/5): DPO on SELF-sampled pairs — the
       model already straddles the boundary; that's where preference learning is real.
     - If you insist on a contrastive repair pair for an all-fail task, `chosen` must
       be a MINIMAL EDIT of the model's own rejected attempt that flips it green — not
       a from-scratch alien reference. That keeps the gradient on the bug, not the style.

2. SPLIT THE TASK SET BY MARGIN, NOT BY "ALL-FAIL." (First Principles reframe; Executor
   + Expansionist routing.) all-fail@K=4 is not "can't" — it's "not at this budget."

   (First Principles + Outsider.) A capability the 8B lacks can only come from outside

POSITION VS PRIOR ART — WHY THIS IS NOT JUST ANOTHER nanoGPT
--------------------------------------------------------------------------------
DO NOT COMPETE where Karpathy's nanoGPT already wins; these fights are lost before
they start: model-code readability (~300 lines, the reference everyone reads),
scale credibility (it reproduces GPT-2 124M on OpenWebText), multi-GPU/DDP and
compile-path speed, and community trust (thousands of forks).

THE REAL GAP: nanoGPT is a REFERENCE IMPLEMENTATION, not an INSTRUMENT. It tells
you the loss went down. It never tells you whether you learned anything. It has no
seed replication, no noise floor, no leakage check, no preregistration — because it
was built to demonstrate an architecture, not to keep a user honest. Every failure
this project hit in its first 24 hours, nanoGPT would have let us walk into with a
clean green loss curve.

THE FIVE WEDGES, ranked by defensibility — each one is already evidenced in this
repo's own history, which is why they are credible rather than aspirational:
  W1 REFUSE TO REPORT A NUMBER YOU KNOW IS FAKE. Scan for train/val overlap before
     training; if val is duplicated from train, say so and decline to print a val
     loss. Strongest wedge: it is the most common way real results turn fake, and
     no training tool does it. Live instance: council §18 finding 2.
  W2 SEEDS BY DEFAULT, NOISE FLOOR REPORTED. k>=5, mean +/- 3 sigma, test-retest
     sigma separated from between-config sigma, and the sentence nothing else says:
     "that improvement is inside noise, it isn't real." Evidence: ~70% of Track B's
     apparent run-to-run spread was measurement noise (§18 finding 4).
  W3 HYPERPARAMETERS THAT FOLLOW THE ARCHITECTURE. nanoGPT hardcodes its LR for its
     own configs. We ship auto_lr(n_embd), backed by a preregistered 5-seed result
     (0.2601 -> 0.1545, 5.3x the bar, §19). Drag the width slider, get a sane LR.
  W4 PREREGISTRATION IN THE RUN LOOP. Write the bar before the run; the tool holds
     you to it after. No product does this because it makes the product look worse.
     That is exactly why it is credible.
  W5 GUI + WINDOWS-FIRST. nanoGPT assumes terminal, Python, config editing. Its
     speed path leans on Triton, which has no working Windows install on this box
     (§18, confirmed by direct attempt). That constituency is unserved.

TWO TRAPS that would make this WORSE than nanoGPT, not better:
  T1 Adding architecture features to look serious (RoPE/SwiGLU/MoE). Our own §19
     experiment showed one hyperparameter beat every architecture option on the
     table by an order of magnitude. Chasing architecture = becoming a worse nanoGPT.
  T2 Claiming to train good models. At this scale we cannot, and saying so plainly
     IS the product. "Small, yours, honest, offline" is defensible.
     "Like GPT but yours" is not.

POSITIONING LINE: nanoGPT teaches you how a transformer works. This teaches you
whether you actually improved it — the scarcer skill.

EXECUTOR'S STRUCTURAL NOTE — THE ONE THING THAT CHANGES BUILD ORDER
--------------------------------------------------------------------------------
The vision fuses TWO DIFFERENT PRODUCTS. Both are buildable. Fused into one
dependency chain, they block each other; separated, they ship.

  PRODUCT A — the from-scratch trainer (V1, V2, V5). REAL TODAY. studio.py trains
    a model from random init on the user's own text, on this hardware, offline.
  PRODUCT B — the local assistant with hands (V3, V4). An AGENT LAYER: reasoning,
    tool use, machine control.

THE CATEGORY ERROR TO AVOID: requiring Product A's model to be Product B's brain.
A 3M-parameter char-level model trained on one person's corpus cannot reason or
drive a computer, and that is not a scale-up away — it is a different category.
Data and compute scale, not architecture, is the binding constraint, and no amount
of local training time crosses it. "Infinite training time" does not fix this:
more epochs on a small corpus overfits, it does not create reasoning.

THE RECONCILIATION, and it is already half-built here: the agent layer is
MODEL-AGNOSTIC. config.py (§12 addendum) already resolves any model from one place.
So Product B is built against whatever model is strongest for the job (a local
Ollama model today), while Product A keeps improving independently — and the
from-scratch model GRADUATES into the agent layer if and when it is good enough,
measured on the ruler rather than assumed. That ordering delivers the whole vision
without either half waiting on the other, and without a false claim in the middle.

WHAT SURVIVES AS THE HONEST PITCH: "A model that has read only what you gave it. It
starts as random numbers. You watch it learn, on your machine, offline, and nothing
leaves your computer" — plus an assistant that can actually act, powered by the best
model available locally, with the user told which is which. Not "your from-scratch
model runs your computer on day one."

SAFETY BOUND ON V4 (name it now, not after something breaks): §3's hard constraints
already put privilege escalation and UAC bypass OUT OF SCOPE, and that stands. A
model with machine control needs an explicit, enumerated permission boundary —
what it may touch, what requires a confirm, what is refused outright — designed
BEFORE the hands are attached, not retrofitted. "Control anything and everything"
is the user's call to make per-action, not a default the software grants itself.

23. PERMANENT GOAL: ONE CLICK .EXE INSTALLER WITH HARDWARE AWARE SETUP
    (2026-07-26, proprietor mandate. STANDING, not a sprint item. This does not
     expire, does not get folded into a round, and is not satisfied by a
     "works on my machine" script.)
--------------------------------------------------------------------------------
THE MANDATE, in the proprietor's terms: the program must be installable as an
.exe. No terminal. No Python install. No pip. No virtualenv. No command line at
any point, ever, for the end user. The installer ASKS QUESTIONS and/or READS THE
DEVICE HARDWARE, and decides how to install based on what it finds.

This is now a permanent acceptance criterion. Any feature added from here is
judged partly on whether it survives that constraint. A feature that only works
when someone types a command is not finished.

WHAT THE INSTALLER MUST DO
  1. DETECT the machine before choosing anything: GPU present or absent, vendor,
     VRAM, driver version, CPU cores, system RAM, free disk.
  2. DECIDE the install profile from that detection:
       - NVIDIA GPU with enough usable VRAM  -> CUDA build of torch.
       - No GPU / unsupported GPU / low VRAM -> CPU only build. This is not a
         failure state. A small character level model trains fine on CPU, just
         slower, and the CPU wheel is a fraction of the download.
       - Pick sane DEFAULTS for the detected machine: model width/depth, batch
         size, context, and precision, so the first run cannot OOM on the user's
         hardware.
  3. ASK when detection is ambiguous or when the tradeoff is genuinely the
     user's: "you have a GPU, but the CUDA download is about 2.5 GB, do you want
     it?" is a legitimate question. "What is your CUDA version?" is not; that is
     the installer's job to work out.
  4. BUNDLE the Python runtime so the user never learns it exists.
  5. VERIFY after installing: run a tiny real training step and confirm it
     completes, before telling the user it worked. Same rule as everywhere else
     in this project. If it was not run, it is not done.

THE TRAP THIS PROJECT ALREADY PAID FOR, and the installer must not walk into it:
  NAIVE VRAM CHECKS LIE ON THIS CLASS OF MACHINE. Council activation #8 (§22,
  finding 4) measured it directly on this box: with driver 591.86, CUDA system
  memory fallback is ENABLED, so allocating 22 GiB against a 15.99 GiB card did
  NOT raise an out of memory error. It silently spilled into host RAM and kept
  running, slowly. §22 finding 5 draws the explicit conclusion: a
  device_map="auto" + mem_get_info() probe "would report a false 'fits' while
  silently spilling, so it cannot answer the question it was built to ask."
  CONSEQUENCE FOR THE INSTALLER: sizing defaults by "did an allocation succeed"
  is invalid. It must read the actual VRAM figure and apply a margin, or disable
  the fallback explicitly before probing. Otherwise the installer will happily
  configure a model that technically runs and is a hundred times too slow, and
  the user will conclude the program is broken rather than misconfigured.
  Also note §22's arithmetic correction: GB and GiB were mixed once already in
  this project and produced a wrong headline number. The installer does its
  capacity maths in ONE unit, stated in the code.

ACCEPTANCE TEST (how we will know this is actually done, not claimed done)
  A person with no Python, no terminal experience, and a mid range Windows
  laptop downloads one file, double clicks it, points it at a folder of their
  own writing, and gets a trained model producing recognisably their-flavoured
  text, without asking anyone for help and without ever seeing a console.
  Ten such people is the real bar (see §21's success measure).
