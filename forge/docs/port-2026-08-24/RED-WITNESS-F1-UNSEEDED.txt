== a second fact these runs establish, which changes how both witnesses read ==
lora_B is bitwise identical in the unseeded pair too (224/224), and max|B| = 0
exactly, in every --max-steps 1 run examined (/tmp/f1_a, /tmp/f1_red_a, /tmp/f1_red_b).
The reason is the schedule, not determinism:

  $ transformers TrainingArguments.get_warmup_steps: ceil(num_training_steps * warmup_ratio)
    --max-steps 1, warmup_ratio 0.1 -> ceil(1 * 0.1) = 1 warmup step
    get_cosine_schedule_with_warmup(warmup=1, total=1) -> lr at the only step = 0.0
    sum(lr) over the run = 0.000000e+00

So an --max-steps 1 run takes exactly one optimizer step at lr = 0. The saved
adapter IS its initialisation: A == A0 exactly, B == 0 exactly. Nothing trained.

Consequences, stated rather than assumed:
  * F1 is UNAFFECTED and in fact cleaner: comparing two initialisations is
    precisely what F1 asks. Green 224/224 vs red 0/224 stands.
  * init_vs_training.py's labels are wrong at --max-steps 1. It prints
    "lora_A (seeded init, then trained)" and a READING clause concluding
    "the divergence is inside the optimisation". At this step count there is
    no optimisation to localise anything to.
  * F9's preregistered liveness gate -- "at --max-steps 1: every lora_B
    nonzero" -- cannot pass on this pipeline as configured, for the same
    reason. It needs warmup_steps=0 or --max-steps >= 2.
