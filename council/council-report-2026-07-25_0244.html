Council Verdict

✔ Where the council agrees

  • The thesis is inverted. A DPO pair needs a passing solution, so all-fail tasks emit zero gradient. The loop trains on near-frontier successes, not failures. (3 advisors, independently — highest confidence.)
  • There is no ruler. Without a held-out eval the loop "closes" whether the model improved or drifted. Unmeasurable = unfalsifiable.
  • Data volume, not the Python env, is the real bottleneck. 3 pairs trains nothing.
  • The durable asset is the verifier-grounded preference factory — the 8B model is disposable.

⚡ Where the council clashes

  • Who feeds the harness. First Principles: stop self-generation, source "chosen" from a stronger generator. Expansionist: keep it autonomous, build a self-expanding flywheel. Split turns on the real goal — a stronger local coder vs. an autonomous data primitive.
  • Measure first vs. scale first. Contrarian: STOP, build the eval. Executor: launch the data run tonight. Reconciled by running them in parallel — but if ordered, the eval wins.

◎ Blind spots caught

  • The conciseness preference is an active reward hack — both pass weak tests, shorter wins, training length bias. Every "scale it" plan would mass-produce that bias silently.
  • Scaling via MBPP still only scales self-solved successes — more of the ceilinged signal.
  • "Self-rewarding" is a misnomer — it's test-rewarded. Naming it honestly changes how its value is judged.

➜ The recommendation

Reframe from "self-improving model" to "verifier-grounded preference-data factory," and build the ruler before scaling the factory: (1) frozen held-out pass@k eval; (2) gate the conciseness reward-hack; (3) scale data via MBPP but inject reference solutions for all-fail tasks so failures become learnable; (4) build the WSL2 + cu121 env in parallel (low priority); (5) prefer ORPO now, GRPO later — skip vanilla DPO's ref-model overhead; train only once a checkpoint beats baseline on held-out tasks.

The one thing to do first

Build the frozen held-out pass@k eval — 30–40 tasks that never enter pair generation, score the base model's baseline today. Until that ruler exists, every other move is unverifiable. Recommended prompt to relay to the executor:

Full Advisor Responses

The Contrarian

The fatal flaw is the ceiling, not the scale. DPO pairs only exist when the model already solves a task; every "chosen" is self-generated — self-distillation with a hard ceiling at existing capability. failures.jsonl is a fiction: all-fail tasks produce zero gradient. "Trains on its own failures" is precisely what it cannot do.

The conciseness pairs are a reward hack in progress: both pass weak hidden tests, shorter is labeled "chosen" — training a bias toward terse code that games under-specified tests. Kill conciseness preferences until there's a robustness signal.

No held-out eval means no proof the loop improves anything; QLoRA DPO on ~3 pairs likely degrades the model and you'd never know. Highest-value move: stop — build a frozen held-out task set and measure pass@k before scaling or training. Build the ruler before the factory.

The First Principles Thinker

"Python 3.14 blocks training" isn't the blocker — 3 pairs trains nothing regardless. The real blocker is structural: a self-rewarding loop can only mint signal from tasks the generator already half-knows; genuine failures produce zero pairs and rot. The generator is both student and teacher and can't teach past itself.

If the goal is a stronger local coder, this loop is close to the least efficient path — an 8B q4 bootstrapping off its own output. The real asset is the objective, test-grounded, adversarially-filtered preference-pair harness; the model is disposable, the verifier is durable.

Move: decouple the halves. Point the harness at a strong generator to mass-produce verified pairs; let the 8B train rather than author its own curriculum.

The Expansionist

The DPO pairs are the byproduct. The crown jewel is a zero-human-label, zero-self-scoring verified-preference factory. Three undervalued upsides: (1) the reward is domain-agnostic — any checkable oracle plugs into the same loop; (2) failures.jsonl is a difficulty-frontier discovery engine mapping the capability edge; (3) the training blocker is a gift — the generator is a standalone data asset; stockpile the JSONL, any env consumes it later.

Move: don't wait on Unsloth. Parallelize K-candidate generation overnight and have the model auto-generate new tasks plus tests, filtered by coverage — a self-expanding corpus. Training is commoditized; the autonomous verified-data flywheel is the moat.

Chair note: multi-domain oracles are future upside but sit outside the current code-repair scope (Section 3) — not advised for pursuit now.

The Outsider

You call this "self-rewarding," but the model never rewards itself — hidden unit tests do. That's just unit tests. The name oversells it; be honest about which thing you're building.

The math is tiny: 6 tasks, 3 pairs. DPO on 3 examples does effectively nothing, so the loop that's the whole point has never closed. What convinces you it scales to thousands? If a human hand-writes each task and its tests, the "autonomous" part is doing a lot of quiet work.

"Trains on its own current failures" — but you make pairs only from successes and bucket the failures. That's the opposite of the tagline. Until the loop closes once end-to-end, is this a self-improving system or a data generator with an aspirational README? What single result would prove it works?

The Executor

The data problem outranks the environment problem — but both can run in parallel. Track A (data, today, no new deps): stop hand-writing tasks; MBPP gives ~970 pure-function problems with hidden tests already shaped like your pipeline. Write a ~20-line adapter, point forge.py at it, run overnight at K=8 — 3 pairs becomes hundreds.

Track B (env, parallel): install Python 3.12 side-by-side, venv, torch from the cu121 index (matches known-good cuda_v12 on driver 591.86 — not cu13), then unsloth/trl/peft; smoke-test torch.cuda.is_available().

Sequencing: launch Track A first (long pole, unattended), set up Track B while it churns. Don't train until ~500 pairs — below that the QLoRA signal is noise.
