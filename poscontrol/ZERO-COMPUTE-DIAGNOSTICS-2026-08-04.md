### 1.5 VERDICT

> **Yes. There is artifact-level evidence that the two served arms are different models, and it is
> unambiguous.** The evidence is: (a) the live `llama3-forged` Modelfile carries an `ADAPTER` line and
> the live `llama3-forged-null` Modelfile carries none, with every other byte — base weight blob,
> chat template, stop tokens, license — identical between them; (b) the blob that `ADAPTER` line points
> at is named with the exact SHA-256 this session computed over `adapter.gguf`, which was converted
> tensor-for-tensor (448 = 448) from the safetensors checkpoint whose digest the preregistration
> recorded 26 minutes before the first replicate; (c) the author's 50,000× amplification control passed
> and I re-verified the amplified checkpoint is a true ×50000 scaling of all 224 `lora_B` tensors.
>
> **And it is corroborated behaviourally from the benchmark rows themselves**: the 31-task profiles of
> the two arms differ far beyond replicate-level noise (permutation p < 5e-5), and an independent
> behavioural counter (unimported-`typing` failures) differs at p = 0.0077.
>
> **The null result is therefore interpretable.** It is not the null of a comparison between two copies
> of the same model. It is a real "the adaptation moved behaviour around without moving the aggregate."
>
> **One residual gap, stated plainly:** nothing *in the 08-02 rows* attests which model file served
> them — the rows carry no model digest, adapter hash, or Ollama version field (`S10`). The
> `adapter_is_live` control was run at export time on 2026-07-28 on a different prompt, not during the
> benchmark. So the artifact chain proves the *trained model was built with the adapter*, and the row
> statistics prove *the two arms behaved differently on 08-02*; the two together close the question in
> practice, but no single delivered artifact ties an individual replicate row to a model digest. See
> §6, C5.

### 3.3 The arm-vs-base gap is an **instrument artifact**, not a model property (`S5b`, `F2`)

This is the most consequential finding after §1, and it dissolves the question the paper was asking.

The base arm's draws contain a **temperature-0 greedy anchor** that the arms' draws do not. Within the
*same base rows*:

* base **greedy** draws: 980 / 1550 correct = **0.6323**
* base **sampled** draws: 3129 / 6200 correct = **0.5047**
* **greedy − sampled = +12.76 pp** on the same model, same tasks, same run.

The base arm additionally pools two verifier populations. 10 of the 50 base rows carry **no `verifier`
key at all** (banked 2026-07-29 19:25–19:44, before the interpreter pin); 40 carry
`version 3.11.9, pinned_away_from_launcher: true, launcher_version 3.14.6`. `ruler_noise.py` refuses to
pool across verifiers by design ("*they are kept in the file as evidence, not pooled*", lines 190–212),
but `analyze_run1.py`'s `load()` pools all 50. The two sub-populations are not exchangeable:

* base 10 pre-pin rows, as published: **0.5910** (sd 0.0222)
* base 40 pinned rows, as published: **0.5150** (sd 0.0381)
* Welch between them: **+7.597 pp, t = 8.217, df = 24.1, p = 1.9e-8.**

* **null vs matched base: +0.157 pp, t = 0.172, df = 69.1, p = 0.864, 95% CI [−1.66, +1.98] pp**

Compare the published-reference versions: trained − base = −3.26 pp (p = 7.4e-4) and null − base
= −3.81 pp (p = 1.8e-5) (`S6`). **The entire apparent "both served arms are ~3.5 pp worse than the
unmodified base" effect is accounted for by (i) the greedy anchor in the base rows, worth −2.55 pp when
removed, and (ii) pooling 10 pre-pin rows scored by a more permissive verifier, worth a further
−1.42 pp when dropped.** Under a matched instrument, **neither served arm is distinguishable from the
unmodified base.**

### 3.4 Answer to the paper's question: template defect, or quantization cost?

> **Neither.** Once the base reference is measured with the arms' own sampler and verifier, **there is
> no deficit left to explain** — the served arms sit on top of the unmodified base (+0.71 pp and
> +0.16 pp, both n.s.). And the trained−null profile is **not a broad uniform shift**: the common-mode
> component is +0.55 pp and explains **0.49% of Σ Δ²**, the signs split 15 up / 14 down / 2 flat
> (sign-test p = 1.0), and the 90% CI on the common-mode is [−0.844, +1.941] pp — a uniform shift
> larger than ≈2 pp is excluded. What *is* present is a genuine, sign-balanced **task-level
> redistribution**: implied true per-task effect sd 6.39 pp after removing sampling noise, with the
> whole-profile permutation test at p < 5e-5.

**Confidence, honestly stated:**

* *"Not a chat-template / EOS serving defect between the arms"* — **very high.** Two independent
  grounds: the byte-diff of the two served Modelfiles shows identical `TEMPLATE` and identical stop
  parameters (§1.1), and the common-mode shift is bounded to ±2 pp by the data (§3.4). A template/EOS
  defect would produce a large one-sided uniform shift; the data excludes one.
* *"The arms-vs-base gap is instrument, not quantization"* — **high, but not airtight.** The greedy /
  sampled split is exact arithmetic on draws the harness recorded separately, and the verifier split is
  a recorded field, so the decomposition itself is not an inference. What is *not* verifiable is that
  nothing else changed between 2026-07-29 (base) and 2026-08-02 (arms) — a 91.35-hour gap with no
  recorded Ollama version, model digest or server build (§6, C8). One loose thread argues for caution:
  the base arm shows a significant downward drift across its own run order (Pearson r = −0.498,
  t = −3.980, df = 48, p = 0.0002; first half 0.5489 vs second half 0.5115, Welch p = 0.0037 — `F7`),
  and that drift is unexplained. The two served arms show no such drift (trained r = +0.141, p = 0.386;
  null r = −0.291, p = 0.069).
* *"There is real per-task structure between the arms"* — **high but with one named confound.** The
  permutation evidence is strong (p < 5e-5, and the observed statistic 84.9 exceeds the maximum of
  20,000 permutations, 76.6). The confound is that the arms ran in **sequential blocks** — trained
  16:51–19:22, null 19:24–20:50 on 2026-08-02 — so any machine-state drift between the blocks is
  perfectly aliased with arm. `F7` finds no significant within-block drift in either arm, which argues
  against a block artifact but does not exclude a step change at the 19:22→19:24 handover. Interleaving
  the arms replicate-by-replicate would remove this; the delivered data cannot.

## 6. What this still cannot show

Every item here is a check I attempted or considered and **could not complete with the artifacts on
disk**. For each, the artifact that would close it is named. Nothing weaker was silently substituted.

**C1 — The Ollama blob's *content* was not hashable, only its *name*.**
The forged Modelfile's `ADAPTER` line names blob `sha256-4107cf60…436a`, which equals the SHA-256 I
computed over `adapter.gguf`. But `C:\Users\t\.ollama\models\blobs\` was not delivered, so I hashed the
export-side file, not the served-side blob. The link rests on Ollama's content-addressing convention.
*Closes with:* `sha256sum` of that one blob file on the author's machine (83 MB, one command, zero
compute).

**C2 — The base tag's own Modelfile was not delivered.**
`ollama show --modelfile` output exists for `llama3-forged` and `llama3-forged-null` but **not for
`llama3:8b-instruct-q4_K_M` itself.** So "the base reference arm was served with the same template and
stop parameters as the two arms" is **unverified** — it is highly likely (both derived arms show the
same base blob and template, and `ollama create FROM <tag>` inherits them), but I did not read it.
*Closes with:* `ollama show llama3:8b-instruct-q4_K_M --modelfile > modelfile_base.txt`.

**C3 — Exact-output agreement between the arms is NOT computable. Confirmed, not assumed.**
I walked every string-valued field in both delivered JSONL files. In `ruler_noise.jsonl` the only string
fields that exist anywhere are `model`, `task_set`, `ts`, `per_task[].tid`, and the three `verifier`
strings; **maximum string length in the entire file is 61 characters** (a filesystem path). In
`eval_history.jsonl` the only strings are `model`, `task_set`, `ts`, `kind`, `per_task[].tid` and two
`frontier[].lane` labels. **No completions, no prompts, no generated code, no diffs were retained
anywhere in the delivered artifacts** — the rows are pure aggregates of binary outcomes. The only raw
model text anywhere in the package is the three strings inside `export_report.json`'s `spot` and
`adapter_is_live` blocks, and those are one non-benchmark prompt from 2026-07-28, not benchmark draws.
Therefore: **"do the two arms produce identical outputs?" cannot be answered from these files, at any
strength.** *Closes with:* retaining completions (or even per-draw output hashes) in the harness — a
one-line change in `eval.py`'s per-draw loop, but it requires a re-run, i.e. new compute.

**C4 — Draws are unpaired; no seed is recorded.**
Neither the rows nor the sampler block carries a generation seed or per-draw identifier, so the 200
trained draws on a task cannot be matched to the 200 null draws. Every comparison here is unpaired at
the draw level (pairing is only possible at the task level, which is what §4.3 does).
*Closes with:* recording the seed per draw; requires a re-run.

**C5 — No row attests which model served it.**
`S10` enumerates every field: there is no model digest, adapter hash, or Ollama version on any of the
130 rows. So the chain "this replicate was produced by a process that had the adapter loaded" is
established by the *artifacts* (§1.1–1.3) and corroborated by the *statistics* (§1.4), but not by a
per-row attestation. *Closes with:* stamping `ollama show --modelfile` digest (or `/api/show`'s
`details.parent_model` + digest) into each row at measure time; requires a re-run for these rows, zero
compute for future ones.

**C6 — Training-seed variance is unavailable, and so is the exact optimizer-step count.**
One checkpoint per arm ⇒ **zero training-seed variance by construction**; `se_diff` has no slot for it,
so nothing here supports a claim about DPO in general (the preregistration says this itself, citing
Dodge et al. 2020 / Bouthillier et al. 2021). Separately, `MANIFEST.txt` records that no
`trainer_state.json`, no checkpoint dirs and no training console log exist on the author's machine after
a full recursive search; `TRAINING_PARAMS_derived.txt` gives **57 or 58** optimizer steps as *arithmetic*
(918 pairs, per-device batch 2 × grad-accum 8), depending on an unrecorded `drop_last`. The observed
step count is **not recoverable**. *Closes with:* 2–3 training seeds per arm (real compute), and
`trainer_state.json` retention going forward (free).

**C7 — The rows do not record which ruler bytes they were served.**
No row carries `ruler_set_sha256`. The 31 tids match `ruler_frozen.json` exactly, and the two frozen
files on disk agree on all 31 `task_sha256` values, but **both freezes (2026-07-30 and 2026-07-31)
postdate the 50 base rows (2026-07-29)** — so for the base arm I can verify the tid *set* but not that
the task *payloads* served on 07-29 were the frozen bytes. The two arms' rows postdate the final freeze,
so they are not exposed to this. *Closes with:* stamping `ruler_set_sha256` into each row (free, going
forward).

**C8 — Nothing records the serving stack across the 91.35-hour gap.**
No Ollama version, server build, driver or GPU state is recorded on any row. The base arm ran 2026-07-29
and both arms ran 2026-08-02. The §3.3 conclusion ("the arm-vs-base gap is an instrument artifact")
holds *given* an unchanged serving stack, which is plausible but unverified — and the base arm's
unexplained within-run downward drift (r = −0.498, p = 0.0002) is a live reason not to treat that arm as
a clean reference at all. *Closes with:* re-measuring the base arm greedy-free under the current stack
(that is new compute, ~2 hours at the observed cadence), or recording the stack version per row (free).

**C9 — No generation metadata, so a template/EOS defect cannot be probed directly.**
The rows carry no stop reason, token counts, truncation flag, or latency. The §3.4 verdict on
"template defect vs quantization" is therefore an inference from (a) the Modelfile byte-diff and (b) the
shape of the delta profile — strong, but not a direct measurement of, say, "how often did generation
stop on `<|eot_id|>` in each arm". *Closes with:* recording `done_reason` / `eval_count` per draw
(free, going forward).

**C10 — The 10 pre-pin base rows cannot be re-scored.**
They carry no verifier record and no completions, so they can neither be pooled honestly nor rescored
under 3.11. They can only be excluded, which is what §3.3's matched reference does. *Closes with:*
completions retention (C3).

**C11 — The arms cannot be de-confounded from run order.**
Trained and null ran as back-to-back blocks (§5.1). No delivered artifact can separate "arm" from "which
half of the evening it was". `F7` shows no within-block drift, which is evidence against a block
artifact, not proof. *Closes with:* interleaving the arms replicate-by-replicate; requires a re-run.

**Count: 11 checks could not be performed with what is on disk.** Seven of the eleven (C1, C2, C5, C7,
C8, C9, C10-as-instrumentation) close with **zero additional compute** — they are recording or one-shot
`sha256sum`/`ollama show` gaps, not measurement gaps. Four (C3, C4, C6, C11) require new runs.

### 6.1 Two defects found in the published analysis path (neither changes the headline null)

1. **`analyze_run1.py` pools the base arm across two verifiers and two samplers.** `load()` groups by
   `model` only, so all 50 base rows are averaged into the published `base M = .5302`, mixing 10 pre-pin
   rows (mean .5910) with 40 pinned rows (mean .5150), p = 1.9e-8 between them, and mixing a
   greedy-blended sampler with the greedy-free estimand the preregistration names as primary
   (`metric.greedy_anchor: false`). `ruler_noise.py` refuses this pooling for the arms; the analysis
   script does not inherit that refusal for the reference arm. **The corrected matched reference is
   0.4905, not 0.5302** (§3.3). *This does not touch the primary result*, which compares trained to null
   and never uses the base rows.
2. **The base reference and the two arms are not the same instrument.** The published narrative reads as
   "base 53.0% vs served arms 49.8%/49.2%", inviting a quantization or serving-loss story. Matched, it
   is "base 49.1% vs 49.8%/49.2%" — **no gap at all.** Any sentence in the paper that treats the
   base-vs-arms difference as a property of the models should be withdrawn or re-derived from the
   matched reference.

### 6.2 What the analysis *can* now support that the paper did not claim

* The two arms **are** different models — artifact-level (§1.1–1.3) and behaviour-level (§1.4,
  permutation p < 5e-5). The null is interpretable.
* The instrument was **live at the arms' own operating point**: 0 dead channels, 28/31 in band (§2.2).
  The preregistration listed this as something it could not show; it is now shown.
* The aggregate effect is **bounded, not merely unmeasured**: TOST rejects a true effect of ±2 pp or
  larger at α = .05 (§4.5).
* The adaptation **redistributed** per-task performance (implied per-task effect sd 6.39 pp) while
  moving the aggregate by 0.49% of the squared-delta budget. "No aggregate effect" and "no effect" are
  different claims, and only the first is supported.

# Independent implementation: regularised incomplete beta by Lentz continued
# fraction, cross-checked below against direct Simpson integration of the t pdf.
def _betacf(a, b, x):
    tiny, eps = 1e-300, 3e-16
    qab, qap, qam = a + b, a + 1.0, a - 1.0
    c, d = 1.0, 1.0 - qab * x / qap
    if abs(d) < tiny: d = tiny
    d = 1.0 / d; h = d
    for m in range(1, 500):
        m2 = 2 * m
        aa = m * (b - m) * x / ((qam + m2) * (a + m2))
        d = 1.0 + aa * d; c = 1.0 + aa / c
        if abs(d) < tiny: d = tiny
        if abs(c) < tiny: c = tiny
        d = 1.0 / d; h *= d * c
        aa = -(a + m) * (qab + m) * x / ((a + m2) * (qap + m2))
        d = 1.0 + aa * d; c = 1.0 + aa / c
        if abs(d) < tiny: d = tiny
        if abs(c) < tiny: c = tiny
        d = 1.0 / d; delta = d * c; h *= delta
        if abs(delta - 1.0) < eps: break
    return h

def _betai(a, b, x):
    if x <= 0.0: return 0.0
    if x >= 1.0: return 1.0
    lb = (math.lgamma(a + b) - math.lgamma(a) - math.lgamma(b)
          + a * math.log(x) + b * math.log(1.0 - x))
    front = math.exp(lb)
    if x < (a + 1.0) / (a + b + 2.0):
        return front * _betacf(a, b, x) / a
    return 1.0 - front * _betacf(b, a, 1.0 - x) / b

def t_sf(t, df):
    """P(T > t)."""
    x = df / (df + t * t)
    tail = 0.5 * _betai(df / 2.0, 0.5, x)
    return tail if t > 0 else 1.0 - tail

def t_sf_simpson(t, df, n=200001):
    """Independent check: numerically integrate the t pdf from t to a far tail."""
    lg = math.lgamma((df + 1) / 2) - math.lgamma(df / 2) - 0.5 * math.log(df * math.pi)
    C = math.exp(lg)
    def pdf(u): return C * (1 + u * u / df) ** (-(df + 1) / 2)
    hi = t + 300.0
    h = (hi - t) / (n - 1)
    s = pdf(t) + pdf(hi)
    for i in range(1, n - 1):
        s += (4 if i % 2 else 2) * pdf(t + i * h)
    return s * h / 3

def t_crit(df, alpha=0.05):
    lo, hi = 0.0, 200.0
    for _ in range(300):
        mid = (lo + hi) / 2
        if t_sf(mid, df) > alpha / 2: lo = mid
        else: hi = mid
    return (lo + hi) / 2

def mean(v): return sum(v) / len(v)
def sd(v):
    m = mean(v); return math.sqrt(sum((x - m) ** 2 for x in v) / (len(v) - 1))

def welch(a, b):
    na, nb = len(a), len(b)
    va, vb = sd(a) ** 2, sd(b) ** 2
    se = math.sqrt(va / na + vb / nb)
    diff = mean(a) - mean(b)
    df = (va / na + vb / nb) ** 2 / ((va / na) ** 2 / (na - 1) + (vb / nb) ** 2 / (nb - 1))
    t = diff / se if se else 0.0
    tc = t_crit(df)
    return dict(diff=diff, se=se, df=df, t=t, p=2 * t_sf(abs(t), df),
                ci=(diff - tc * se, diff + tc * se), tc=tc)

def paired(a, b):
    d = [x - y for x, y in zip(a, b)]
    n = len(d); se = sd(d) / math.sqrt(n)
    t = mean(d) / se if se else 0.0
    tc = t_crit(n - 1)
    return dict(diff=mean(d), se=se, df=n - 1, t=t, p=2 * t_sf(abs(t), n - 1),
                ci=(mean(d) - tc * se, mean(d) + tc * se), sd=sd(d))

    ma, mb = mean(a), mean(b)
    num = sum((x - ma) * (y - mb) for x, y in zip(a, b))

def rank(v):
    order = sorted(range(len(v)), key=lambda i: v[i])
    r = [0.0] * len(v); i = 0
    while i < len(order):
        j = i
        while j + 1 < len(order) and v[order[j + 1]] == v[order[i]]: j += 1
        avg = (i + j) / 2 + 1
        for k in range(i, j + 1): r[order[k]] = avg
        i = j + 1
    return r
